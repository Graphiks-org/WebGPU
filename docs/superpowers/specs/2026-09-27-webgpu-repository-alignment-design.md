# WebGPU repository alignment with Kalligraphie

## Intent and scope

Bring `Graphiks-org/WebGPU` to functional parity with the repository conventions used by [Kalligraphie](https://github.com/Graphiks-org/Kalligraphie), while keeping WebGPU-specific content, module names, Maven coordinates, and existing release credentials. A new contributor should be able to discover the API, run its business tests, build its documentation, submit a conforming PR, and understand how releases are published. The reference baseline is WebGPU `master` at `762c250` (2026-09-27), where the group is already `org.graphiks` and the modules are `webgpu-api`, `webgpu-descriptors`, `webgpu-specifications`, and `webgpu-web`.

Functional parity means equivalent contributor experience and automation, not copying Kalligraphie's font, shaping, or golden-test content. The user explicitly excluded reproducible regeneration checks: fetching specifications, LLM enrichment, and regenerating bindings remain documented manual operations and are not PR gates.

## Repository documentation

Replace the minimal root README with a WebGPU entry point following Kalligraphie's structure: project identity and status, badges for relevant CI and license, a concise description, published modules and `org.graphiks` Maven coordinates, a verified consumer example, supported targets, verification and documentation commands, and links to contribution, support, security, changelog, and technical guides. Move the current step-by-step specification refresh and binding-generation instructions into a dedicated maintenance guide. Keep the exact existing Gradle task names, including the misspelled `tranform-json-doc-to-yaml`, until a separate compatibility change is designed.

Add a `:docs` Gradle module and a MkDocs Material site under `docs/`. The site contains English and French navigation and WebGPU-specific pages for introduction, getting started, module architecture, type mapping, testing, and specification maintenance. The existing `TYPE_MAPPING.md` remains the canonical mapping document; the site links to or incorporates that source without a second independently edited mapping. API reference for the public modules is generated by Dokka and embedded into the MkDocs tree through `:docs:embedDokkaIntoMkDocs`, matching the contributor command in Kalligraphie. Generated API output and `_site/` are ignored, not committed. Site generation is local and does not fetch WebGPU specifications.

## Community and contribution files

Add `CHANGELOG.md`, `CONTRIBUTING.md`, English and French `CODE_OF_CONDUCT`, `SECURITY`, and `SUPPORT` files, issue templates for bugs and feature requests, and a PR template. Adapt all links, contact routes, target names, commands, and changelog instructions to WebGPU. Do not assert an unverified support address or security mailbox; use GitHub's repository security advisory route and issues/discussions only where the destination exists. The changelog starts from the current state without inventing historical release notes.

Adopt Kalligraphie's PR policy as an adapted GitHub workflow plus a repository policy file and validation script. It checks Conventional Commit titles and authored commit subjects, the PR template's required sections and one selected change type, an explicit changelog decision, and branch naming. Scopes correspond to WebGPU modules and repository responsibilities. Accepted branch prefixes include the established `feat/`, `fix/`, and `chore/` conventions and `codex/`, which this repository already uses. The written policy and workflow enforce the same rules. Repository branch-protection settings are outside versioned files and are described for maintainers rather than assumed active.

## Business tests and CI

Retain the current Kotlin business tests for WebGPU buffers, enums, and JS/Wasm interop. Update CI so that PRs and `master` run the appropriate existing Gradle checks on Linux, macOS, and Windows, with explicit platform-specific tasks only where the current module configuration supports them. Validate public API compatibility using the existing ABI validation setup for published modules. Any new tests in this work must cover an observed business behavior gap or a changed consumer example; no generator-output golden tests, regeneration-diff gate, specification download, or LLM server is added to CI.

The CI workflows use least-privilege permissions and avoid duplicate cache layers. Documentation builds on PRs serve as validation but do not deploy. The test and docs checks provide distinct status signals; publication depends on successful relevant checks or runs its own equivalent verification before uploading.

## Documentation and Maven publication

On `master`, a docs workflow generates Dokka, builds MkDocs, uploads `_site/`, and deploys GitHub Pages. It also supports manual dispatch. The Pages environment and repository setting may need to be enabled by a maintainer after merging; the workflow must report a clear failure if external configuration is absent.

Keep Maven Central publication from `master` snapshots, `v*` release tags, and manual snapshot dispatch. Use the existing `org.graphiks` group, renamed WebGPU module coordinates, and existing secret names (`SONATYPE_LOGIN`, `SONATYPE_PASSWORD`, `PGP_PRIVATE`, `PGP_PASSPHRASE`). Align the snapshot default with the Gradle project version instead of the stale `0.0.10-SNAPSHOT` workflow text. Validate that snapshot and release versions have the expected form before publishing. Update POM URLs and SCM metadata to `Graphiks-org/WebGPU`, preserve MIT licensing and the known developer attribution, and build/test before publication. No release or Pages deployment is triggered during implementation or spec review.

## Validation and completion criteria

- The README's module names, Maven snippets, Gradle commands, links, and examples match the current source and settings.
- English and French docs navigation resolves; `:docs:embedDokkaIntoMkDocs` and `mkdocs build -f docs/mkdocs.yml` complete locally or in the docs CI job.
- Existing business tests and ABI checks pass for the platform tasks actually declared by Gradle; CI matrices do not name missing tasks.
- PR-policy fixtures cover accepted and rejected title, branch, template, and changelog cases, and the workflow invokes the same validator.
- Publish workflows reference the existing secrets and current modules, validate versions, and can be inspected without pushing a tag or uploading artifacts.
- No automatic specification fetch, LLM call, or binding regeneration is introduced into `check`, PR CI, or publication.

## Implementation boundaries

The work consists of three reviewable parts: documentation and community files; business-test and PR-policy CI; and docs/Maven publication. They share the README and Gradle settings but can be validated separately before integration. External GitHub Pages settings, branch protection, and Maven credentials remain repository administration tasks; the repository documents their required state without embedding secrets.
